LogoMotive on Windows

LogoMotive builds natively on Windows from the same sources as macOS and Linux — no WSL, no virtual machine. It needs MSYS2, which supplies the compiler and libraries. Everything on this page has been run on a real machine; where it hasn't, the page says so.

The short version

In the MSYS2 shell for your CPU — CLANGARM64 on ARM, UCRT64 on Intel/AMD:

git clone https://github.com/hansolovkarlsson/LogoMotive.git
cd LogoMotive
./scripts/install_gtk.sh
make run

If that worked, you can stop reading. Step 3 is the one people get wrong, so start there if it didn't.

1

What you need

The same three libraries every other platform needs, plus a way to get them on Windows:

  • GTK4 — the windowing toolkit. This is the big one.
  • SDL2 — sound and joystick input. Not optional, even if you never make a sound: the interpreter links against it unconditionally.
  • pkg-config — how the Makefile finds the other two.
  • A C compiler and make.
  • MSYS2 — which provides all four, plus the POSIX shell the Makefile needs for mkdir -p and its $(shell …) probes.

Why MSYS2 and not Visual Studio? GTK4 has no supported MSVC build, and the Makefile is a plain POSIX makefile. MSYS2 gives you both a working GTK4 and the shell to drive it. The binary it produces is a normal native Windows .exe — it is not a Cygwin-style emulation layer, and it does not need MSYS2 present to run once bundled (see step 8).

2

Install MSYS2

Download the installer from msys2.org and run it, or from a terminal:

winget install MSYS2.MSYS2

The default location is C:\msys64. The installer picks the right build for your CPU automatically.

3

Pick the right shell

This is the step that trips people up, and it's worth understanding rather than just copying. MSYS2 installs several shells, each building for a different target. They look identical. Opening the wrong one is the most common way this goes wrong.

Open the one matching your CPU from the Start menu:

  • ARM64 (Snapdragon, Surface Pro X…) — open MSYS2 CLANGARM64. Its packages are prefixed mingw-w64-clang-aarch64-.
  • Intel or AMD, 64-bit — open MSYS2 UCRT64. Its packages are prefixed mingw-w64-ucrt-x86_64-.

Not sure which you have? Settings → System → About, under System type. Or in any MSYS2 shell:

echo $MSYSTEM

That prints the environment the shell is currently in — the same variable install_gtk.sh reads to decide what to install.

Don't use the plain "MSYS2 MSYS" shell. It's the odd one out: it builds POSIX-emulation binaries against msys-2.0.dll and has no native GTK4 at all, so nothing here will work from it. install_gtk.sh detects this specific mistake and tells you which shell to open instead, rather than failing halfway through an install.

4

Get the source

pacman -S --needed git
git clone https://github.com/hansolovkarlsson/LogoMotive.git
cd LogoMotive

Every command on this page runs from the project root — the directory holding Makefile.

Cloning with Windows Git instead? That works too. Git for Windows ships with core.autocrlf=true, which would normally give you a CRLF working tree, but the repository's .gitattributes overrides that and pins line endings to LF. That matters: one test reads an example script off disk and compares interpreter output byte-for-byte, and a stray carriage return makes it fail on Windows and nowhere else.

5

Install the dependencies

The bundled script reads $MSYSTEM and installs the correctly-prefixed packages for your environment:

./scripts/install_gtk.sh

No sudo needed — MSYS2's pacman runs as you. Afterwards it checks that the compiler and make really are present rather than assuming, so a missing one is reported immediately instead of three commands later in the middle of a compile.

Or do it by hand. On CLANGARM64:

pacman -S --needed \
    mingw-w64-clang-aarch64-clang \
    mingw-w64-clang-aarch64-gcc-compat \
    mingw-w64-clang-aarch64-pkgconf \
    mingw-w64-clang-aarch64-gtk4 \
    mingw-w64-clang-aarch64-SDL2 \
    make

On UCRT64, swap the prefix and take a real gcc instead of clang:

pacman -S --needed \
    mingw-w64-ucrt-x86_64-gcc \
    mingw-w64-ucrt-x86_64-pkgconf \
    mingw-w64-ucrt-x86_64-gtk4 \
    mingw-w64-ucrt-x86_64-SDL2 \
    make

What's gcc-compat? The Makefile asks for gcc, and the CLANG environments don't have one — they have clang. gcc-compat provides a gcc that wraps it, so the same makefile works unchanged. UCRT64 has a real gcc, so it doesn't need this.

Want to check what you've got before building? These print a version number if the library is installed and fail if it isn't:

pkg-config --modversion gtk4
pkg-config --modversion sdl2
6

Build and test

make

That produces bin/logomotive.exe. On CLANGARM64 it builds with no warnings at all. What matters is that it finishes without an error.

To confirm the build is sound rather than merely complete:

make test

Eight test binaries build and run. All eight should end the same way:

All tests passed.

These are headless — no window opens and none is needed.

7

Run it

make run

Builds if needed, then opens the window: turtle canvas on one side, history pane and entry box on the other. Type REPEAT 4 [FD 100 RT 90] into the entry box and press Enter.

Once built, you can run the binary directly, optionally handing it a script:

./bin/logomotive.exe
./bin/logomotive.exe examples/sample.logo

Headless mode works from cmd.exe and PowerShell as well as the MSYS2 shell:

bin\logomotive.exe --headless examples\lists.logo

Menus and shortcuts match Linux rather than macOS: the menu bar is inside the window, and the modifier is Ctrl. Ctrl+O open · Ctrl+S save · Ctrl+E export PNG · Ctrl+Shift+O/Ctrl+Shift+S bytecode · Ctrl+Plus/Ctrl+Minus/Ctrl+0 text size · Ctrl+Shift+I hide the input pane · Ctrl+Q quit. File dialogs are the native Windows ones.

8

Share a build with someone

The .exe alone won't run on a machine without MSYS2 — it needs about sixty GTK and SDL DLLs beside it, plus some data files GTK looks up by path. One script collects all of it:

./scripts/bundle_windows.sh

That writes a self-contained folder under dist/ — roughly 50 MB — containing the executable, its full DLL closure, the gdk-pixbuf image loaders, GTK's compiled settings schemas, and the examples. Zip that folder and it runs on any Windows machine of the same architecture.

Every CI build publishes one of these automatically, for both architectures, under the run's Artifacts — so you can also just download a build rather than making one.

9

Troubleshooting

target not found: gtk4 from pacman

You're following Linux instructions on Windows. MSYS2 has no bare gtk4 package — every native package carries an environment prefix, as in step 5. Older copies of install_gtk.sh produced this exact error on Windows by mistaking MSYS2's pacman for Arch's; pull the latest main if you see it from the script itself.

Package gtk4 was not found in the pkg-config search path

Almost always the wrong shell — the packages are installed for one environment and you're building in another. Check echo $MSYSTEM against step 3.

make: gcc: command not found

On a CLANG environment, the gcc-compat package is missing. See step 5.

Exit code 127, or the program exits instantly with no message

In an MSYS2 shell, 127 usually means a missing DLL — but it can also mask a crash. Run the binary from PowerShell instead, which reports the real code: -1073741571 (0xC00000FD) is a stack overflow, and means a build without the Makefile's Windows stack flag. Pull the latest main.

--help or --headless prints nothing in a console

Fixed on 2026-08-14. GTK4 links the program as a GUI-subsystem binary, and Windows gives such a process no console even when a console launched it, so output went nowhere while the program still exited 0. It now attaches to the launching console at startup. Redirecting to a file or piping always worked, and still does. Pull the latest main.

A script's SHOW or TEXT output has odd blank lines

A .logo file saved with CRLF line endings by a Windows editor, on a build from before 2026-08-14. Source is normalised on load now, so any editor's line endings work. Pull the latest main.

LOADPIC: could not load

Image paths are resolved relative to the working directory, not to the script. Run from the directory holding the image, or give a full path.

10

What's actually been tested

Stated precisely, so you know what you're relying on:

  • Windows 11 on ARM64, CLANGARM64 — verified 2026-08-14 by hand, on clang 22.1.8, GTK 4.22.4 and SDL2 2.32.10. Clean build with zero warnings, all 8 suites passing, the GUI drawing with menus present, Ctrl+O opening the native file dialog, --headless correct to a console and to a file and through a pipe, and a bundled copy running with MSYS2 entirely off PATH.
  • Windows on x86-64, UCRT64 — verified 2026-08-14 by CI rather than by hand, no Intel or AMD machine having been available: clean build, all 8 suites, and the dependency and bundling scripts both exercised on their UCRT64 paths. It uses a real gcc rather than clang, which if anything is the better-trodden path. The one thing CI can't check is the GUI — it has no screen — so the window itself is verified on ARM64 only.
  • Windows 10 — untested. Nothing is known to be wrong; nobody has run it.
  • MSYS2 MINGW64, CLANG64, MINGW32 — install_gtk.sh knows their package names and they resolve, but nothing has been built with them. UCRT64 is the recommended x86-64 environment.

If you build it somewhere not on this list, say so on the issue tracker — working or not, that's useful.

Built alongside LogoMotive's own C interpreter — see the repository for the source, the language design docs, and the full changelog.
